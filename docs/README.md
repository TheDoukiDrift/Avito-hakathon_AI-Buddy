# AI-buddy — ИИ-наставник для стажёров

Прототип ИИ-помощника для адаптации стажёра в команде: ответы о процессах и
инструментах (RAG), чек-лист адаптации со статусами и следующими шагами,
оформление отсутствий через имитацию корпоративного сервиса. Кейс Авито,
хакатон Hack&Change 2026.

## Возможности (сценарии)

- **S1 «Спроси бадди»** — RAG-ответы по базе знаний с цитированием источников,
  контекст роли и поддержка follow-up вопросов.
- **S2 «Оформи отсутствие»** — бадди объясняет процедуру, уточняет детали,
  показывает черновик заявки, после подтверждения создаёт её через имитацию
  сервиса отсутствий и показывает статус.
- **S3 «Мой чек-лист»** — этапы адаптации, статусы задач, следующие шаги,
  напоминания о просроченных шагах.
- **S4 «К кому обратиться»** — маршрутизация к наставнику, HR BP или
  руководителю; недоступные роли сведения не раскрываются.
- **S5 «Прогресс стажёра»** — статус чек-листа подопечного для наставника.
  Реализуем при наличии времени, первым приоритетом среди дополнительного
  скоупа: эксперт подтвердил спрос менторов на видимость прогресса (Q&A,
  01:11:58).

Все четыре роли — стажёр, наставник, руководитель и HR BP — поддержаны в
интерфейсе и в матрице прав.

## Архитектура

```
Пользователь
    │
    ▼
React (чат) ──POST/SSE──► FastAPI
                            │
                            ▼
                    Агент (system prompt + история + контекст роли)
                       │                    │
                       ▼                    ▼
                 RAG retriever          MCP-клиент
                                             │
                                             ▼
                            MCP-сервер (FastMCP, отдельный процесс)
                                             │
                                             ▼
                            имитации корп. сервисов
                            (OpenAPI-контракты, PostgreSQL)
                       │
                       ▼
              стрим токенов (SSE) ──► UI
```

Агент не имеет прямого доступа к доменным сервисам: единственный путь —
MCP-инструменты, каждый из которых проверяет роль пользователя.

Стек:

- **Backend:** Python 3.12, FastAPI, Alembic, pydantic v2.
- **Данные:** PostgreSQL 16 + pgvector, Redis 7.
- **Frontend:** React 18 + TypeScript + Vite, Zustand, TanStack Query, Zod.
- **MCP:** FastMCP (отдельный процесс) — единственный канал агента к доменным
  сервисам.
- **Интеграции:** OpenAPI-имитации корпоративных сервисов (FastAPI + PostgreSQL).
- **Инфраструктура:** Docker Compose.
- **LLM:** OpenAI-совместимый API через env, оффлайн-фолбэк `FakeLLM` (по
  умолчанию в `docker-compose`).

## Быстрый старт

```bash
git clone <URL репозитория>
cd Avito-hakathon_AI-Buddy
cp .env.example .env
docker compose up --build
```

После запуска откройте http://localhost:3000.

Пример `.env` (секретов в репозитории нет):

```dotenv
POSTGRES_USER=avito
POSTGRES_PASSWORD=avito
POSTGRES_DB=ai_buddy
DATABASE_URL=postgresql+psycopg://avito:avito@postgres:5432/ai_buddy
REDIS_URL=redis://redis:6379/0
LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=qwen2.5-72b-instruct
MCP_SERVER_URL=http://mcp:8001
```

Полный список переменных — в `.env.example`. Внутри `docker compose` БД и Redis
доступны по именам сервисов (`postgres`, `redis`), MCP-сервер — по `mcp`.

`LLM_API_KEY` можно оставить пустым — тогда используется оффлайн-стаб `FakeLLM`
и прототип работает без внешнего ключа.

Инструкция по подключению реального LLM-ключа для проверки — в разделе
«Внешние API».

## Тестовые учётные данные

Данные синтетические, пароль у всех учётных записей `test1234`. Роли
проверяются на бэкенде и в MCP-инструментах.

| Логин | Роль |
|---|---|
| `intern@example.com` | стажёр (intern) |
| `mentor@example.com` | наставник (mentor) |
| `manager@example.com` | руководитель (manager) |
| `hr.bp@example.com` | HR BP (hr_bp) |

### Матрица прав

| Действие / сведение | intern | mentor | manager | hr_bp |
|---|---|---|---|---|
| Ответы бадди по базе знаний | + | + | + | + |
| Свой чек-лист: просмотр и выполнение | + (свой) | + (просмотр подопечных) | + (просмотр команды) | + (все) |
| Заявка на отсутствие: создание | + (своя) | + (своя) | + (своя) | + (своя) |
| Заявка на отсутствие: согласование | – | + (подопечные) | + (команда) | + (все) |
| Заявка на отсутствие: просмотр | + (свои) | + (подопечные) | + (команда) | + (все) |
| Контакты участников | + (своей команды) | + | + | + |
| Данные о зарплате и бенефитах | – | – | – | – |
| Аудит событий | + (свои) | + (подопечного) | + (команда) | + |

Бенефиты и финансовые сведения исключены полностью — вне области задачи кейса.
Матрица зафиксирована в `docs/DECISIONS.md` и покрыта отдельными RBAC-тестами.

## Порядок проверки сценариев (для экспертов)

0. Запуск без ключа: `LLM_API_KEY` можно не задавать — поднимется `FakeLLM`; с
   ключом в `.env` используется реальная модель.
1. Войти как стажёр, открыть чат, спросить «как оформить отгул?» — ожидается
   ответ с процедурой и ссылкой на источник.
2. Продолжить: «оформи отгул завтра» — бадди уточняет детали, показывает
   черновик, после подтверждения создаёт заявку через сервис отсутствий и
   показывает статус.
3. Открыть «Мой чек-лист» — этапы, статусы, следующие шаги.
4. Спросить «кто занимается командировками?» — маршрутизация к HR BP или
   наставнику.
5. Проверка прав: войти как стажёр, попросить данные, доступные только
   наставнику, — бадди отказывает и предлагает обратиться к наставнику.
6. Проверка RBAC: войти как `hr.bp` и убедиться, что доступна своя матрица
   данных, а запросы вне роли отклоняются. Повторить для `mentor` (только
   подопечные) и `manager` (команда).

## Тесты и покрытие

```bash
docker compose exec backend pytest --cov=app --cov-report=html --cov-report=xml
docker compose run --rm --build frontend-test   # vitest в стадии сборки frontend
```

Покрытие ≥80% меряется раздельно: бэкенд — pytest, фронтенд — Vitest. Код
имитаций корпоративных сервисов в прикладное покрытие не входит. Отчёт любого
стандартного формата (coverage.py HTML/XML, Istanbul) — артефакт CI.

- **Бэкенд** — pytest + coverage, ≥80% строк прикладного кода команды
  (исключены миграции, сиды и сгенерированный код). Отчёты `htmlcov/` и
  `coverage.xml` — артефакты CI.
- **Фронтенд** — Vitest, ≥80% по слоям `store/utils/api`.
- **Тайминг** — отдельный тест-замер проверяет, что локальные операции чтения из
  БД/кэша укладываются в <1 с; вызовы LLM не блокируют UI (SSE-стрим).

Запуск всего одной командой:

```bash
make test
```

## Внешние API

| Параметр | Значение |
|---|---|
| Сервис | OpenAI-совместимый LLM API |
| Модель | задаётся переменной `LLM_MODEL` |
| Переменная окружения | `LLM_API_KEY` (и `LLM_BASE_URL`) |
| Пример конфигурации без секретов | `.env.example` |

Жюри проверяет прототип без GPU и создаёт собственный ключ по нашей инструкции
(провайдер, модель, переменная окружения). По умолчанию `docker compose`
поднимается с `FakeLLM` — прототип проверяем и офлайн. Подтверждено экспертами:
внешние OpenAI-совместимые API допустимы, офлайн-откат достаточен (Q&A,
00:49:47, 00:52:35, 00:53:58).
