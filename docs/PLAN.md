# AI-buddy — план проекта (Hack&Change 2026, кейс Авито)

Внутренний документ команды: что делаем, зачем и в каком порядке. Публичная
инструкция по запуску — в `README.md`.

## 1. Гипотеза ценности

**Если** мы поможем стажёру получать ответы о процессах и выполнять
организационные действия через ИИ-ассистента с доступом к базе знаний и
корпоративным сервисам (имитациям), **то** стажёр быстрее перейдёт к
самостоятельным задачам, а наставник потратит меньше времени на повторяющиеся
объяснения (базовая занятость наставника — 40–48 ч за 6-месячную программу),
**потому что** информация из разных систем собирается в одну точку входа, а
рутинные действия выполняются через бадди без отвлечения коллег.

## 2. Разбор задачи (PSW, этап Dive)

| Блок | Содержание |
|---|---|
| Контекст | Зачем: адаптация стажёра упирается в разрозненные источники. Чек-лист новичка разбросан по сервисам, процедуры описаны в разных местах, за мелочами идут к наставнику. Пример из кейса — оформление отгула. Наставник тратит 40–48 ч за программу на повторяющиеся объяснения. |
| Критерии успеха | Оценка по 6 критериям онлайн-этапа: внедряемость и интеграции 30%, UX 25%, работоспособность сценариев 20%, техническая реализация 15%, безопасность и данные 5%, продуктовая презентация 5%. На финале: ценность 20%, демонстрация 25%, обоснованность 20%, внедряемость 25%, защита/ответы 5%. Итог: онлайн 40% + финал 60%. |
| Пространство решений | Минимум для зачёта: чат + чек-лист + хотя бы одно действие через MCP-имитацию корпоративного сервиса. Опционально: дашборд наставника со статусом подопечного. Отрезаем всё, что не усиливает заявленные сценарии. |
| Ограничения | Только синтетические/анонимизированные данные, без реальных HR-систем. Rights-aware: не раскрывать и не выполнять то, что недоступно роли пользователя. Сценарии с чувствительными персональными данными и финансовыми операциями — вне скоупа. Покрытие >80% строк собственного кода команды с воспроизводимым отчётом. SDD-спеки для AI-функций. UI <1 с для локальных операций. Вызовы LLM и внешних сервисов — асинхронно со статусом ожидания, без блокировки UI. |
| Стейкхолдеры | Эксперты жюри (проверяют и запускают), стажёр (основной пользователь), наставник (снимаем нагрузку), руководитель стажёра, HR BP. |
| Источники | Чек-лист стажёра Авито, AvitoTech Playbook, публикации на Хабре, дизайн-система Авито. |

## 3. Сценарии

**S1 «Спроси бадди».** RAG-ответы о процессах и инструментах с учётом контекста
роли и ссылками на источники. Поддерживаются follow-up вопросы в рамках диалога.

**S2 «Оформи отсутствие» (глубокий, пример из кейса).** Бадди ведёт по
практическим шагам, а не только отвечает: объясняет процедуру отгула с учётом
ТК РФ → уточняет дату и причину → показывает черновик заявки →
**подтверждение пользователем** → действие через MCP-инструмент к имитации
сервиса отсутствий → показывает результат и сохранённый статус. Цепочка
согласования — руководитель, затем HR BP (в компаниях с HR administration —
HR admin); оба шага видны в интерфейсе. При отказе или ошибке сервиса —
корректная обработка: понятное сообщение, заявка не создаётся или помечается
как неуспешная.

**S3 «Мой чек-лист».** Этапы адаптации, статусы задач, следующие шаги,
напоминания. Имитация ИИ-крона: раз в N минут проверка просроченных шагов.
Контент чек-листа строим по структуре адаптации из ответа организаторов, а не
по догадкам: неделя 1 — цели, план и критерии успеха с руководителем; неделя 2
— инструмент отслеживания прогресса от куратора; далее — 1:1 с наставником,
обучение, ревью компетенций, экватор, выпускной (`DECISIONS.md`, ADR-13).

**S4 «К кому обратиться».** Маршрутизация: бадди отвечает сам, либо предлагает
обратиться к наставнику, HR BP или руководителю. Сведения, недоступные роли
пользователя, не раскрываются.

**S5 «Прогресс стажёра» для наставника.** Статус чек-листа подопечного и
частые вопросы. Реализуем при наличии времени, приоритет первый среди
дополнительного скоупа: эксперт подтвердил спрос — наставнику и руководителю
нужна видимость прогресса адаптации в системе, а не через пингование человека
(01:11:58).

S5 идёт после рабочего состояния S1–S4, но раньше любых других улучшений
(`DECISIONS.md`, ADR-14). Все четыре роли — `intern`, `mentor`, `manager`,
`hr_bp` — реализуем полностью: это строгое прочтение раздела кейса об
участниках адаптации, а сценарии для наставника и руководителя эксперт называет
плюсом (00:11:37). S2 остаётся глубоким сценарием; S1, S3, S4 и S5 доводим до
рабочего состояния. Количество сценариев само по себе оценку не определяет —
важна полнота заявленного функционала и глубина проработки.

## 4. Маппинг на критерии оценки

| Критерий | Что делаем |
|---|---|
| Внедряемость и интеграции — 30% | MCP-сервер инструментов отдельным процессом с явными контрактами, OpenAPI-имитации корпоративных сервисов, стек PostgreSQL/Redis/React, совместимый с Авито, явный API-клиент вместо скрытых вызовов. Имитации тонкие, без тестового портала: усилие идёт в сценарии, а не в корпоративный контур. |
| UX — 25% | SSE-стриминг со статусом ожидания, локальные операции <1 с (с автоматическим замером), чат и чек-лист в одном интерфейсе. |
| Работоспособность сценариев — 20% | S1–S5 проходятся end-to-end для всех четырёх ролей, поднимается одной командой `docker compose up` — без ключа LLM. |
| Техническая реализация — 15% | pytest с покрытием ≥80% по бэкенду и Vitest ≥80% по фронтенду (по слоям `store/utils/api`), раздельные отчёты в CI, формат отчёта любой; имитации в покрытие не входят; SDD-спеки (OpenSpec), тест-замер локальных операций <1 с. |
| Безопасность и данные — 5% | Роли проверяются на бэкенде, синтетические данные, подтверждение перед действиями, аудит событий. |
| Продуктовая презентация — 5% | Готовим на этапе Impact по плану. |

## 5. Архитектура (выбранный вариант: LLM-агент с tool calling + RAG)

### Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| A. Детерминированный intent-пайплайн без агента | Предсказуем и прост, но слабо показывает работу с ИИ и интеграциями — теряем баллы за внедряемость и техническую реализацию. |
| B. LLM-агент с tool calling + RAG | **Выбран.** Показывает и ИИ, и интеграции, и при этом обозрим за 7 дней. |
| C. Графовый агент на LangGraph | Оверкилл для четырёх сценариев: сложность растёт, выигрыша для демонстрации нет. |

### Компоненты

**`backend/`** — Python 3.12, FastAPI, асинхронный. Слои: API → агент
(оркестрация LLM) → MCP-клиент → MCP-сервер → доменные сервисы-имитации.
Прямого доступа из агента к доменным сервисам нет: единственный путь —
MCP-инструменты. Alembic для миграций, pydantic v2 для схем.

**MCP-сервер инструментов (FastMCP) — отдельный процесс.** Поднимается в
`docker-compose` самостоятельным сервисом и служит единственным каналом агента
к корпоративным сервисам. Инструменты: `absence.create`, `absence.status`,
`absence.list`, `absence.approve`, `checklist.get`, `checklist.complete`,
`contacts.lookup`, `kb.search`. Каждый инструмент проверяет роль и права
пользователя — авторизация на уровне инструмента, не на уровне промпта.

**RAG.** PostgreSQL + pgvector, чанкинг документов базы знаний. Оффлайн-фолбэк
BM25 для тестов без эмбеддингов.

**Имитации корпоративных сервисов.** FastAPI-сервисы с OpenAPI-контрактами на
каждый домен: отсутствия (заявки со статусами и согласованием), чек-лист
новичка, контакты участников. Хранение — PostgreSQL, синтетические данные в
сидах. MCP-сервер оборачивает эти сервисы как инструменты, поэтому требование
«оформляйте действия через MCP» выполнено буквально, а замена имитации
реальным сервисом сводится к смене base URL.

**LLM.** OpenAI-совместимый клиент, конфигурация через переменные окружения
`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` (внешний API: сервис, модель и
переменная окружения — по требованию кейса). По умолчанию `docker compose up`
поднимается с `FakeLLM`-стабом и работает без ключа; при заданном
`LLM_API_KEY` используется реальная модель. Вызовы LLM асинхронные и никогда
не блокируют UI: мгновенный статус ожидания + SSE-стрим токенов.

**Хранилища.** PostgreSQL — пользователи и роли, диалоги, прогресс чек-листа,
заявки, `audit_events`. Redis — сессии, rate-limit, кэш ретрива.

**`frontend/`** — React + TypeScript, Vite, Zustand (чат, чек-лист), TanStack
Query (API), Zod (валидация контрактов), SSE-стриминг ответов. Тесты — Vitest,
порог ≥80% по слоям store/utils/api.

### Поток запроса

```
Пользователь
    │
    ▼
React (чат) ──POST/SSE──► FastAPI ──► Агент (system prompt + история + роль)
                                          │                    │
                                          ▼                    ▼
                                   RAG retriever         MCP-клиент
                                                               │
                                                               ▼
                                     MCP-сервер (FastMCP, отдельный процесс)
                                                               │
                                                               ▼
                                     имитации корп. сервисов
                                     (OpenAPI-контракты, PostgreSQL)
                                          │
                                          ▼
                                стрим токенов (SSE) ──► UI
                                          │
                                          ▼
                                audit_events (параллельно)
```

Прямого доступа из агента к доменным сервисам нет: единственный путь —
MCP-инструменты, каждый из которых проверяет роль пользователя.

### Роли и права

Роли: `intern` (стажёр), `mentor` (наставник), `manager` (руководитель),
`hr_bp` (HR BP) — реализуются все четыре. Матрица прав (`DECISIONS.md`)
определяет, что роль видит и что может делать; проверка выполняется в
MCP-инструментах и API, а не в промпте, и покрыта отдельными RBAC-тестами с
негативными проверками на каждый запрещённый доступ.

### Модель данных

`users`, `roles`, `kb_documents` (+ `chunks`/`embeddings`),
`checklist_templates`, `checklist_items`, `checklist_progress`,
`absence_requests`, `conversations`, `messages`, `audit_events`.

## 6. Стек и обоснование

- **FastAPI вместо Flask.** В кейсе упомянут Python + Flask, но оценивается
  совместимость архитектуры со стеком Авито, а не конкретный язык. FastAPI даёт
  async и SSE из коробки — это критично для неблокирующего UI.
- **pgvector вместо отдельного вектор-стора.** PostgreSQL уже в стеке Авито —
  меньше компонентов, выше внедряемость.
- **MCP отдельным процессом (FastMCP).** Кейс прямо рекомендует MCP — получаем
  явные контракты и возможность заменить имитацию реальным сервисом; инструменты
  изолированы от агента процессной границей, права проверяются на стороне
  сервера инструментов, а не в промпте.
- **Тонкие имитации, без тестового портала.** Адаптер с OpenAPI-контрактом и
  JSON-моки или таблицы в PostgreSQL достаточны; полноценный портал заявок и
  отдельные Jira/Confluence не делаем — эксперт прямо называет это лишним.
- **LLM: OpenAI-совместимый API через env, оффлайн-фолбэк `FakeLLM` по
  умолчанию.** Один и тот же код работает и с внешним провайдером (эксперт
  подставляет свой ключ), и без сети — воспроизводимость проверки не зависит от
  наличия ключа. Локальной модели в образе нет: у проверяющих нет GPU; в README
  — подробная инструкция по подключению ключа.
- **Zustand + TanStack Query + Zod.** Ровно стек из кейса.

## 7. План на 7 дней (Dive → Create → Impact)

| День | Работы |
|---|---|
| Д1 (Dive) | Фиксация PSW и гипотезы, CJM стажёра, выбор сценариев, макет UX, вопросы на Q&A, скелет репозитория и `docker-compose` с заглушками. |
| Д2 | Каркас backend (FastAPI, модели, Alembic, сиды), MCP-инструменты, имитация сервиса отсутствий, матрица прав + RBAC-тесты. Каркас frontend (Vite, роутинг, лейаут чата). |
| Д3 | RAG (ингестия базы знаний, ретривер, faithfulness-чек), S1 end-to-end с `FakeLLM`, тесты. |
| Д4 | S2 целиком (агент + tool calling + подтверждение действия + статусы), контракт-тесты имитации, Playwright-смоук. |
| Д5 | S3 (чек-лист, прогресс, имитация крона) + S4 (маршрутизация, права на инструментах). |
| Д6 | UX-полировка (стриминг, статусы ожидания, ошибки), сиды из настоящего чек-листа Авито (импорт разрешён), нагрузочная/тайминг-проверка локальных операций <1 с, покрытие >80% и coverage-отчёт, README, воспроизводимость Docker с нуля на чистой машине. |
| Д7 (Impact) | Метрики и способ проверки эффекта, видеодемонстрация (путь от запроса до результата), продуктовая презентация, репетиция защиты. |

Д3 — выполнено: ингестия 10 документов, BM25-ретривер, faithfulness 10/10.

Д4 — выполнено: tool loop на реальном LLM (накопление и исполнение `tool_calls`
через слой сервисов), политика подтверждения в системном промпте, «подтверждаю»
обрабатывается детерминированно (последний свой черновик → `pending_approval`),
относительные даты считаются в Europe/Moscow, тесты на stub-LLM без сети.

Д5 — выполнено: S3 — `next_item` по `(week, position)` в ответе чек-листа,
таблица `reminders` (миграция 0004, `started_at` прогресса), имитация
ИИ-крона (`REMINDER_INTERVAL_SEC`, `REMINDER_OVERDUE_DAYS`, разовый запуск
`python -m app.services.reminder_cron`), `GET /api/reminders` и ack без дублей,
напоминания и следующий шаг в ответе агента на обоих LLM-путях. S4 —
`route_question` (KB-hit → ответ базы, иначе или при маркерах эскалации →
наставник → руководитель → HR BP), 7-й MCP-инструмент `contacts_route`,
fallback «Не нашёл в базе знаний…» с контактом. Стек зафиксирован в
`docs/STACK.md`.

Каждый день заканчивается сборкой в одну версию, проходом главного сценария и
коротким созвоном на 10–15 минут (по тренингу Create).

## 8. Метрики пользы и способ проверки

- **Self-service rate** — доля вопросов, решённых без наставника; целевой
  ориентир ≥60% типовых.
- **Median time-to-answer** и доля ответов с корректной ссылкой на источник
  (RAG faithfulness; ручная выборка ≥30 ответов).
- **Completion rate действий (S2)** — доля заявок, оформленных без доработки.
- **Скорость прохождения чек-листа** против baseline без бадди (симуляция на
  тестовых персонах).
- **CSAT** — оценка ответа по шкале 1–5.
- **Экономия часов наставника** — модель от базы 40–48 ч.

Проверка: юзабилити-тесты на синтетических персонах, A/B-симуляция (сценарий с
бадди против ручного пути), события в `audit_events` (имитация Clickstream).
Честно: долгосрочный эффект — гипотеза для пилота, в MVP его не обещаем.

## 9. Риски и допущения

| Риск | Митигейшн |
|---|---|
| Зависимость от LLM | `FakeLLM`-стаб для тестов и оффлайна, провайдер-нейтральный OpenAI-совместимый клиент. |
| Жюри без GPU и со своим ключом | `FakeLLM` по умолчанию — прототип работает без ключа и без GPU; в README подробная инструкция по подключению ключа (провайдер, модель, переменная). Локальной модели в образе нет. |
| Галлюцинации действий | Подтверждение всех мутаций, allowlist инструментов, проверка прав на бэкенде. |
| Не хватит времени на 4 сценария | S5 отрезаем первым, S2 приоритетнее остальных. |
| Не успеть с покрытием 80% | Тесты пишем вместе с кодом, а не в конце; фронтенд тестируем с первого дня, имитации в покрытие не входят. |
| Нет ответов организаторов на Q&A | Закрыт: ответы Q&A от 2026-11-10 разобраны в `ref/qa_answers.md` и внесены в `DECISIONS.md`; без ответа остались только видео и порог <1 с — по ним действует строгая трактовка. |
| Неопределённость требований к имитациям | Закрыт: достаточно адаптера с OpenAPI-контрактом, MCP тоже ок; тестовый портал не нужен. Имитации тонкие, усилие — в сценарии (00:58:55, 01:10:13; ADR-02). |

## 10. Строгие трактовки неоднозначностей

Часть неоднозначностей закрыта ответами Q&A-вебинара от 2026-11-10 (транскрипт
`ref/qa_transcript.md`, сводка — `ref/qa_answers.md`) и письменными ответами
организаторов. Прямого ответа нет только по двум пунктам — видеодемонстрация и
порог <1 с; там действует строжайшее прочтение требований кейса. Развёрнутые
обоснования и цитаты — в `DECISIONS.md`.

| Неоднозначность | Принятое решение | Обоснование | Статус |
|---|---|---|---|

## 11. Вопросы организаторам и принятые трактовки

Все вопросы, кроме двух (требования к видео и порог <1 с), закрыты ответами
Q&A-вебинара от 2026-11-10 (транскрипт `ref/qa_transcript.md`, сводка —
`ref/qa_answers.md`) и письменными ответами организаторов. По двум оставшимся
действует строжайшее прочтение требований кейса (подробности — в
`DECISIONS.md`).

1. Допустим ли внешний OpenAI-совместимый API (OpenRouter/GigaChat) — эксперты
   запускают своим ключом через нашу переменную окружения? Достаточно ли
   оффлайн-фолбэка (мок/локальная модель) для проверки без ключа?
   *Трактовка:* делаем оба режима — env-конфигурация и `FakeLLM` по умолчанию.
   *Ответ:* внешний OpenAI-совместимый API допустим, оффлайн-фолбэка достаточно
   (00:53:58); ключ передавать не нужно — указываем провайдера и подробную
   инструкцию, организаторы создают ключ сами (00:52:35); у проверяющих нет GPU
   (00:49:47). См. `ref/qa_answers.md`.
2. Какие ожидания к формату имитации корпоративного сервиса — достаточно
   адаптера с OpenAPI-контрактом в Postgres, или нужен отдельный MCP-сервер как
   процесс?
   *Трактовка:* делаем оба — сервисы с OpenAPI и отдельный MCP-процесс.
   *Ответ:* достаточно адаптера с OpenAPI-контрактом, обязательного Postgres
   нет; MCP-сервер тоже ок; тестовый портал разрабатывать не надо (00:58:55,
   01:10:13). Для прототипа допускается имитировать API инструментов и
   оформлять действия через MCP, инфраструктуру заново создавать не нужно;
   перечень внутренних MCP-инструментов не предоставляют.
3. Что считается «простой локальной операцией» для требования <1 с — только
   чтение из БД или и первый токен стрима?
   *Трактовка:* чтения из БД/кэша <1 с с автотестом; LLM не блокирует UI.
   *Ответа нет:* на Q&A вопрос остался без содержательного ответа (01:01:53);
   действует строгая трактовка.
4. Покрытие >80% меряется раздельно по бэкенду/фронтенду или суммарно? Входят
   ли миграции и SDD-спеки? Какой формат отчёта принимается?
   *Трактовка:* раздельно, оба ≥80%, миграции и сиды исключены, HTML+XML.
   *Ответ:* 80% меряется раздельно по бэкенду и фронтенду; код веб-интерфейса
   входит, имитации не входят; формат отчёта любой (01:00:27, 01:08:40,
   01:10:13). См. `ref/qa_answers.md`.
5. Достаточно ли OpenSpec/spec-kit в репозитории как SDD-спецификаций
   AI-функций?
   *Трактовка:* OpenSpec в `specs/` с README-описанием структуры.
   *Ответ:* обязательного шаблона нет — схемы, диаграммы, пошаговый план;
   предпочтение эксперта в сторону spec-kit, OpenSpec тоже допустим (01:00:27,
   01:11:20).
6. Требования к видеодемонстрации: длительность, формат, обязательные моменты?
   *Трактовка:* видео 2–3 мин MP4 плюс живое демо на защите.
   *Ответа нет* — прямого ответа по видео не прозвучало; действует строгая
   трактовка.
7. Финал: тайминг защиты, живое демо или видео?
   *Трактовка:* готовим оба формата.
   *Ответ:* защита перед экспертами Авито; тайминг и формат показа письменно
   не уточнены.
8. Чек-лист стажёра по ссылке — актуальная версия? Можно импортировать в
   тестовые данные?
   *Трактовка:* сид из настоящего чек-листа, файлы в репозитории.
   *Ответ:* ссылка актуальна, импорт в тестовые данные разрешён (00:45:11).

9. Есть ли эталонная матрица прав (что недоступно стажёру, доступно

   *Трактовка:* собственная строгая матрица + RBAC-тесты.

   ориентир — RBAC/ABAC по образцу GCP/AWS IAM (00:33:36, 00:34:53).
10. Достаточно ли ролей «стажёр» + «наставник», или ждут всех участников

    *Трактовка:* все четыре роли.
    *Ответ:* «стажёр + наставник» может быть достаточно, «Up to you»; сценарии

11. Бенефиты (ДМС, компенсации) — считаются финансовыми операциями вне скоупа

    *Трактовка:* справочные ответы допустимы, финансовые операции вне скоупа.
    *Ответ:* справочные ответы о бенефитах допустимы, финансовые операции можно
    мокать; чужие суммы закрываются RBAC/ABAC (00:08:32–00:10:28).
12. Один глубокий сценарий vs 3–5 — влияет ли на оценку работоспособности?
    *Трактовка:* реализуем четыре сценария, S2 — глубоко, S5 — при наличии
    времени.
    *Ответ:* рекомендация — топ-5 «два попроще, одно посложнее, два средних»;

13. Обязателен ли backend на Go, или можно Python (в кейсе упомянут Flask)?
    *Ответ:* «Писать backend на Go необязательно. Вы можете выбрать любой
    удобный для вас язык и стек разработки»; Python с Flask — «можно». Наш
    выбор Python/FastAPI подтверждён (Q&A, 00:53:58).
14. Есть ли требования к каналу взаимодействия — обязателен ли мессенджер?
    *Ответ:* «Ограничений нет. Формат взаимодействия команда выбирает
    самостоятельно… Веб-чата вполне достаточно, использование мессенджера само
    по себе не даёт дополнительных преимуществ при оценке». Веб-чат
    подтверждён, Telegram-бот не нужен (Q&A, 00:53:58).
15. Нужно ли реализовывать корпоративную систему заявок (например, на
    отсутствие)?
    *Ответ:* моделируем процесс сами: создание заявки, отображение статуса,
    получение результата согласования; полноценная корпоративная система не
    требуется. Заявка на доступы может включать проект, обоснование и уровень
    прав (чтение/редактирование/администрирование), согласующий зависит от типа
    ресурса (владелец проекта, руководитель, DevOps). Для отсутствий уровни
    прав не нужны. Согласование отгула: руководитель → HR BP (или HR admin),
    сроки по ТК РФ (00:27:00–00:29:38).
16. Какая цель приоритетнее — скорость выхода стажёра или разгрузка наставника?

    *Ответ:* неделя 1 — обсуждение с руководителем целей, плана, критериев

    прогресса (цели, задачи, ожидания, ход адаптации). В занятость наставника
    входят встречи 1:1, работа с куратором, обучение, ревью компетенций,
    обратная связь, экватор, выпускной; детальной разбивки по часам нет.
    Используем как каркас чек-листа, сид — из настоящего файла (ADR-07,
